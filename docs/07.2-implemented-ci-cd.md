# CI/CD Guide

This guide explains the project's automated checks, container image publishing and failure investigation. It is intended for teammates who did not implement the workflows.

Last updated: October 26, 2026.

## 1. What is implemented?

The project uses **GitHub Actions** to validate changes and publish Docker images.

- **Continuous integration (CI):** tests code, validates configuration, builds containers and runs the synthetic pipeline.
- **Continuous delivery:** publishes images from validated `main` commits to GitHub Container Registry (GHCR).
- **Deployment:** automatic deployment to a Linux/Kanto target is not implemented yet.

The six validation checks and both image-publishing jobs have passed in GitHub Actions, as reported during implementation. The initial integration workflow was merged through PR #27 and publishing through PR #28.

## 2. Workflow files and triggers

| File | GitHub Actions name | When it runs | Responsibility |
|---|---|---|---|
| `.github/workflows/ci.yml` | CI | Pull requests, pushes to `main`, or manual execution | Backend/Python tests, JSON/Compose validation and two Docker builds |
| `.github/workflows/integration-test.yml` | Pipeline integration | Pull requests, pushes to `main`, or manual execution | Run the services and test the synthetic signal/event pipeline |
| `.github/workflows/publish-images.yml` | Publish container images | Completion of either validation workflow on `main` | Check both results for the same source commit, then publish eligible images |

A push to a feature branch with an open PR triggers the PR checks. Publishing is restricted to successful **push validations on `main`**; a successful PR run or manually dispatched validation does not qualify by itself.

## 3. The six checks

| Check | What happens | What passing establishes |
|---|---|---|
| Backend tests | Sets up Java 21 and runs `bash ./mvnw --batch-mode --no-transfer-progress clean verify` from `backend/` | The backend compiles, its configured Maven checks pass and it packages successfully |
| Python unit tests | Sets up Python 3.12, installs test dependencies, generates Protobuf modules and runs pytest with integration tests excluded | The collected tests pass without requiring running external services |
| Configuration validation | Parses Git-tracked JSON files and runs Docker Compose configuration validation | JSON syntax and the Compose model are valid |
| Docker build (provider) | Builds the simulator provider image using Compose | The provider image can be built on a clean AMD64 runner |
| Docker build (autonomous-health-app) | Builds the Velocitas application image, including its model-generation build step | The application image can be built on a clean AMD64 runner |
| Synthetic pipeline integration | Starts the stack, executes the obstruction/recovery demo, and runs nine live KUKSA publication checks | The tested synthetic pipeline produces the expected state transitions and valid signal values |

The first five checks belong to **CI**. The sixth belongs to **Pipeline integration**. Docker builds execute as two matrix jobs, which is why the PR displays six checks in total.

Passing configuration validation does not prove that credentials, remote endpoints or runtime behaviour are correct. Passing a Docker build does not prove that the application starts; the integration job covers startup and the selected running pipeline.

### Why generate Protobuf modules?

The source schemas are committed under `uprotocol/proto/`. Generated Python modules, such as `common_pb2.py`, are intentionally ignored under `uprotocol/generated/`.

A clean runner therefore generates these files before pytest imports the transport module. Do not commit generated files to fix a missing-module error. Regenerate them from the committed schemas.

These Python tests include the existing in-process Protobuf transport. Passing them does not demonstrate a real networked uProtocol deployment.

## 4. What the integration test does

The integration job runs this synthetic path:

**Python simulator → KUKSA databroker → Velocitas application → Mosquitto/MQTT**

It uses the existing `scripts/run-autonomous-mvp-demo.sh` script, which:

1. Builds and starts the Compose stack.
2. Waits for the simulator control API and application container.
3. Receives a `HEALTHY` event on `sdv/autonomy/status`.
4. Injects `LIDAR_OBSTRUCTION` into `vehicle-001` through the simulator HTTP API.
5. Waits for `EMERGENCY_BRAKING`.
6. Clears the scenario and waits for `HEALTHY` recovery.

The initial healthy event provides evidence that the application can receive signals and publish an event, beyond merely observing a running container.

After the demo, pytest reads these nine KUKSA signals:

| Signal | Test expectation |
|---|---|
| Speed | Value from 0 to 120 |
| Battery state of charge | Value from 0 to 100 |
| Engine coolant temperature | Value from 0 to 150 |
| Tire pressure | Value from 0 to 34 |
| Coolant pressure | Numeric value from 100 to 220 |
| Front LiDAR obstacle distance | Numeric value from 0 to 250 |
| LiDAR health | Boolean |
| Obstacle warning | Boolean |
| Autonomous braking | Boolean |

For exact paths and assertions, read `vehicle-simulator/tests/test_kuksa_publication.py`. These are broad publication/type/range checks, not physical sensor calibration tests.

### Integration configuration and limits

- Compose project: `sdv-ci`.
- Vehicle: `vehicle-001`; one provider, one broker and one vehicle application.
- Simulator HTTP port: `8090`.
- Host KUKSA port: `55556` (container port `55555`).
- Publication interval: one second to accelerate the synthetic scenario.
- Startup fault mode: disabled.
- Demo command timeout: 12 minutes, followed by forced termination if needed.
- KUKSA pytest timeout: two minutes.
- Whole job timeout: 25 minutes.

The workflow attempts to print service status and recent logs and then remove its Compose services/volumes regardless of earlier step success. Forced runner termination can prevent final cleanup steps; GitHub-hosted runners are temporary.

The local demo intentionally leaves services running. The CI workflow adds teardown after the demo.

## 5. How image publishing works

After either main validation workflow finishes, the publishing workflow checks:

1. The triggering run came from a push to this repository's `main` branch.
2. That run succeeded.
3. Both `ci.yml` and `integration-test.yml` succeeded for the exact same commit SHA.

If the other validation is still running, publication is skipped. Its later successful completion triggers another eligibility check. A skipped publishing run during this sequence can be normal. If one required validation fails, the commit is not eligible.

The publishing jobs check out the eligible source SHA explicitly, build the images, push them and verify their remote manifests. They use `GITHUB_TOKEN` with package-write permission; no personal access token is configured by this implementation.

### Published image names

```text
ghcr.io/ankit-suman-07/qa-sdv-project-provider:sha-<FULL_COMMIT_SHA>
ghcr.io/ankit-suman-07/qa-sdv-project-autonomous-health-app:sha-<FULL_COMMIT_SHA>
```

- Replace `<FULL_COMMIT_SHA>` with the full validated main commit SHA, not the PR number or a shortened hash.
- Images currently target **`linux/amd64`**.
- Source repository and commit revision are attached as image labels.
- No `latest` or semantic-version tag is created by this workflow.
- An existing SHA tag is skipped rather than intentionally overwritten by this workflow. Registry tags themselves are not an enforced immutability mechanism; deployment should retain the image digest when exact identity matters.
- The workflow builds again from validated source; it does not promote the exact images used by the integration job. Dependencies/base-image changes can affect a later rebuild.

Find packages through the GitHub owner/repository package views. Each publishing job also writes its image reference in its Actions summary. Package visibility and access permissions must be configured appropriately for the target user or deployment machine.

Publishing images makes them available for deployment. It does not deploy them or prove that a pulled GHCR image runs correctly on the eventual target.

## 6. Normal teammate workflow

1. Create a focused branch from an updated `main`.
2. Implement the change and run relevant local checks.
3. Push and open a PR targeting `main`.
4. Inspect all six checks under the PR's **Checks** view.
5. Fix failures on the same branch; pushing updates reruns the checks.
6. Request review and merge after successful checks and approval.
7. For a release/delivery checkpoint, inspect the main validation and publishing runs, then record the SHA-tagged images.

Required-check enforcement is a separate repository setting. Confirm branch protection or rulesets require the intended checks; adding workflow files alone does not enforce merge restrictions.

Changing workflow display/job names may require updating configured required checks. Changing validation workflow names or filenames also requires reviewing the publishing trigger and eligibility script.

## 7. My PR failed — what do I do?

1. Open the PR and select the failed check's details.
2. Expand the first failed step and read its error, not only the final exit code.
3. Reproduce that step locally where possible.
4. Fix the source, dependencies, configuration or workflow on the existing branch.
5. Run the relevant local check, commit and push.
6. Confirm the replacement run passes. Do not disable a test simply to make the PR green.

| Symptom | Likely area to investigate |
|---|---|
| `ModuleNotFoundError: common_pb2` | Protobuf generation did not run or output/import paths differ |
| `JSONDecodeError` | The named tracked JSON is empty or contains invalid syntax |
| pip resolution or installation error | Dependency pins, supported Python versions, wheel availability or package-index connectivity |
| Maven compilation/test failure | Backend source/test errors or dependency resolution; read Maven's first relevant error |
| Docker build failure | Expand the failing Dockerfile layer; check dependencies, build context and model generation |
| No healthy event | Check provider, broker, application and MQTT startup/connectivity |
| No emergency-braking event | Check scenario HTTP response, distance progression, provider logs and application events |
| Signal test fails | Check VSS definitions, provider publication, data type and broker endpoint |
| GHCR push denied | Check workflow package-write permission, package ownership/access and repository policy |
| Publishing skips | Confirm both successful push runs refer to the same main SHA; check for unfinished/failed validation |

Example: the first CI run could not import `common_pb2` because local generated files were absent on the clean runner. The fix was to generate all committed `.proto` schemas before pytest, preserving the tests and keeping generated files ignored.

For integration failures, inspect **Show service status and logs** in the same run. Publishing failures must be investigated in **Publish container images**, separately from the six validation checks.

## 8. Useful local commands

Run from the repository root in the project's activated Python environment. Use Python 3.12 and Java 21 to match the test runner. Start Docker Desktop/the Docker daemon for container checks.

### Backend

```bash
cd backend
bash ./mvnw --batch-mode --no-transfer-progress clean verify
cd ..
```

### Python setup and tests

```bash
python -m pip install -r requirements-test.txt
mkdir -p uprotocol/generated
python -m grpc_tools.protoc \
  -I uprotocol/proto \
  --python_out=uprotocol/generated \
  uprotocol/proto/common.proto \
  uprotocol/proto/health_status.proto \
  uprotocol/proto/vehicle_status.proto \
  uprotocol/proto/vehicle_fault.proto \
  uprotocol/proto/vehicle_diagnostic.proto
python -m pytest -q -ra -m "not integration"
```

Do not install the Velocitas application's separate requirements over this environment merely to reproduce the unit-test job. Its dependencies are built in its own Docker environment.

### Configuration and image builds

```bash
docker compose -f vehicle-simulator/docker-compose.yml config --quiet
docker compose -f vehicle-simulator/docker-compose.yml build provider
docker compose -f vehicle-simulator/docker-compose.yml build autonomous-health-app
git diff --check
```

Validate an individual JSON file with `python -m json.tool path/to/file.json`. The workflow checks all tracked JSON files and reports invalid filenames.

### Running the synthetic integration locally

Ensure ports `8090`, `55556` and `1883` are available. A distinct Compose project name isolates container names, not host ports. Do not run this alongside another stack using those ports.

```bash
export COMPOSE_PROJECT_NAME=sdv-local-integration
export SIMULATED_VEHICLE_ID=vehicle-001
export SIMULATOR_CONTROL_PORT=8090
export PUBLISH_INTERVAL_SECONDS=1.0
export INJECT_FAULT=0

sh scripts/run-autonomous-mvp-demo.sh

DATABROKER_HOST=127.0.0.1 DATABROKER_PORT=55556 \
  python -m pytest -q -ra -m integration \
  vehicle-simulator/tests/test_kuksa_publication.py

docker compose -f vehicle-simulator/docker-compose.yml down

unset COMPOSE_PROJECT_NAME SIMULATED_VEHICLE_ID SIMULATOR_CONTROL_PORT
unset PUBLISH_INTERVAL_SECONDS INJECT_FAULT
```

If a command fails, inspect logs and run teardown before leaving the environment. The Linux CI command uses GNU `timeout`; the commands above omit that utility so the local demo also works on macOS without installing it.

Local Docker builds on an ARM Mac do not establish AMD64 compatibility. The publishing workflow explicitly builds AMD64; native ARM64 delivery remains separate work.

## 9. What is not covered yet?

- CARLA integration or GPU-based tests.
- Multiple live vehicle brokers/applications in the current integration job.
- End-to-end Ditto, fleet dashboard, OpenSOVD or real networked uProtocol validation.
- Kanto runtime deployment and automatic target updates.
- Post-deployment health verification and rollback.
- ARM64 publishing/validation.
- Automated vulnerability scanning, image signing or promotion of exact tested image artifacts.

These limitations define the present coverage; they do not mean every item is required in the next PR.
